# 暗房配液台

纯前端暗房工具（React + TypeScript + Vite），顶部入口切换三个互不影响的功能：

- **配液计算**：输入稀释式 `1+n`、目标总量、量筒容量与显影罐数量，
  实时算出浓缩液与清水体积，并把超出量筒容量的液体拆成「若干满量筒 + 最后余量」的量取步骤，
  同时生成适合打印的配液卡。**所有数字均由 `src/lib/dilution.ts` 现场计算，无任何写死的结果。**
  结果合法时可经结果区「存入容量台账」入口把本次参数随批次一键建档，免去手工重抄。
- **容量台账**：为每批药液建立「额定容量（等效胶片数）」台账，
  逐次登记实际冲洗量，随时掌握一批药液还能处理多少胶片，
  避免凭记忆继续使用已经耗尽的药液。
- **安全灯测试**：更换安全灯、灯距或相纸后，用阶梯曝光实测可安全操作的时长，
  避免凭经验判断导致相纸起雾。创建测试后按曝光顺序列出各条带时长，
  观察首条出现可见灰雾的条带并完成评估，领域服务据此判定安全上限。

同批处理多只显影罐时，整批工作液只计算一次，再按罐均分领取：目标总量与浓缩液分别均分，
不能整除的余量依次补给前面的罐，每罐清水 = 该罐目标量 − 该罐浓缩液，因此各罐总量相差
不超过 1 mL，且各罐汇总严格还原整批结果，避免逐罐重算造成取整累计偏差。

## 启动（Docker Compose）

```bash
docker compose up --build web
# 默认访问 http://localhost:5173

# 宿主端口由 WEB_PORT 覆盖：
WEB_PORT=8080 docker compose up --build web
# → http://localhost:8080
```

## 一次性验收（Vitest + Playwright）

`verify` 服务会先等 `web` 健康检查通过，再运行 Vitest 单元测试与 Playwright 端到端测试
（通过 `E2E_BASE_URL=http://web` 直接访问 compose 网络内的页面），跑完即退出：

```bash
docker compose run --rm verify
# 等价于：docker compose --profile verify up --build --abort-on-container-exit
```

本地无 Docker 时也可手动执行同一链路：

```bash
npm ci
npm run test        # Vitest（计算规则 + 渲染冒烟）
npm run test:e2e    # Playwright（自动构建并起 preview 服务器）
```

## 输入边界

| 字段           | 合法范围                |
| -------------- | ----------------------- |
| 稀释式 `1+n`   | `n` 为 1–99 的整数      |
| 目标总量 (mL)  | 100–5000 的整数         |
| 量筒容量 (mL)  | 100–5000 的整数         |
| 显影罐数量     | 1–20 的整数（默认 1）   |

非法输入（越界、小数、非数字、留空）会在对应字段下方就地提示，且旧配液卡立即消失，
不会残留过期结果；全部字段合法后才重新计算并展示。

## 计算规则

- 浓缩液精确值 = 目标总量 ÷ (n+1)，以 0.5 mL 为界四舍五入到整数（0.5 进位）；
- 清水量 = 目标总量 − 取整后的浓缩液，因此两者之和恒等于目标总量；
- 单项液体超过量筒容量时拆成若干满量筒加最后余量；恰好等于容量（或其整数倍）时
  不生成零余量步骤；
- 分罐：整批只算一次工作液，目标总量与浓缩液分别按罐均分，余量依次补给前面的罐；
  每罐清水 = 该罐目标量 − 该罐浓缩液，各罐总量相差不超过 1 mL，各罐汇总严格还原整批结果；
- 界面同时给出校验行：每一步 ≤ 量筒容量，且所有步骤合计严格等于目标总量；
- 罐数大于 1 时结果区按罐展示两种液体与量取步骤，勾选进度覆盖全部分罐步骤，
  任一参数变化都会清空勾选；打印卡使用同一分配结果列出每罐明细。

## 容量台账

从顶部「容量台账」入口进入，与配液计算相互独立：

- **创建批次**：填写药液名称与额定容量（整批可处理的等效胶片总数，正整数）；
  空名称、容量留空 / 非整数 / 非正整数 / 超出安全整数范围的超长数字会在对应字段下方就地说明原因，不创建批次。
- **从配液结果建档**：配液结果合法时，结果区出现「存入容量台账」入口；
  填写批次名称与额定处理容量并确认后，批次连同**配液来源快照**（稀释比例、目标总量、
  量筒容量、分罐数及浓缩液 / 清水体积，取自同一次计算并固定保存）一并写入，
  随后自动切换到台账并选中该批次展示来源摘要。名称或容量校验失败时在配液页就地说明原因，
  不切换页面、不写入台账；任一配液参数变为非法时入口随结果一同消失。
  手工创建的批次没有快照，不显示来源摘要；旧版本存储（无快照字段）照常读取。
- **登记用量**：选中批次后登记本次处理的等效胶片数量与备注（可选）；
  每条记录写入前都按**当前有效容量**重新计算剩余量（有效容量 − 已登记用量之和），
  数量留空 / 非整数 / 非正整数 / 超出安全整数范围 / 超过剩余容量时就地说明原因，不写入记录。
- **容量更正凭证**：建档时把额定可处理胶片数写错时，选中批次可追加一张
  **不可修改、不可删除**的容量更正凭证，固定记录批次、原有效容量、新有效容量、
  更正原因与该批内的提交顺序。新容量必须为正的安全整数，且**不得低于该批已登记用量**
  （调减的最低边界就是已登记用量，恰好相等时剩余为 0）。
  批次的创建容量与历史使用记录的 `remainingAfter` 一律保持原样、不被重写；
  后续登记与余量展示按最新有效容量计算，耗尽批次也可凭调增恢复使用。
- **台账展示**：批次列表实时显示累计用量、剩余容量、**有效容量**与状态
  （剩余为 0 即「已耗尽」，否则「使用中」）；有凭证的批次同时标注创建容量；
  选中批次可按时间查看每条使用记录（时间、数量、备注、登记后剩余量）
  与每张容量更正凭证（顺序、原值 → 新值、原因、时间）。
- **不可修改**：使用记录与更正凭证一旦写入即冻结，界面不提供编辑或删除入口；
  批次与记录整体保存在 localStorage，刷新后还原同一台账。
  读取存档时除逐字段结构校验外，还会按「凭证与用量发生的顺序」**分阶段重放容量轨迹**：
  批次 id 必须唯一、每批在任一阶段的累计用量不得超过当时的有效容量、
  每条记录的「登记后剩余量」必须与按顺序重放到该条（所处阶段容量）的轨迹一致、
  更正凭证序号连续 / 容量链不断裂 / 阶段锚点不越界——
  **不能拿最终的新容量反验更正之前的记录**。批次选择、历史余量、耗尽判断与后续写入
  都依据这同一份轨迹。轨迹自相矛盾的存档（同 id 批次、超额批次、与所处阶段矛盾的
  记录余量、断链凭证）视为不可信：就地提示、不作为可写台账、任何普通操作都不会写回
  覆盖原文。旧档没有更正凭证时仍按原规则恢复（有效容量即创建容量）。
  写入前做一次序列化 → 反序列化往返校验：无法被原样读回的状态（如超长数字）拒绝写入，
  保留存储中的旧台账，避免一次异常数据让刷新后整份台账消失。
- **跨标签并发**：多个浏览器标签页同时打开同一台账时，持久化文档带单调递增的
  修订号（revision）。每次提交都「重读存储最新台账 → 核对基准修订号 →
  在最新台账上重放命令 → 修订号 +1 原子写回」：
  - 另一页面已提交（修订号不一致）时，本次动作**整体拒绝**，不覆盖、不删除任何记录，
    顶部就地说明「台账已被其他页面更新」，并把本页对齐到存储中的最后完整台账；
    因此两页从同一剩余量交错登记时，容量永远不会为负，每条成功记录都可追溯，
    旧页面的提交也不会回滚另一页面刚创建的批次或新增记录。
  - localStorage 写入被拒（配额不足 / 安全策略）时，同样**只拒绝当前动作**：
    界面不显示「登记成功」、不扣减余量，存储保留提交前的完整台账，刷新后照旧；
    释放空间后用原输入重试即可落账。
  - 其他标签页写入后，当前页通过 `storage` 事件自动刷新批次列表、记录顺序与剩余量，
    无需手动重载；所有页面最终显示同一批次集合、记录顺序与剩余量。
  - 领域规则拒绝（非法数量、超过**最新**剩余容量、新有效容量低于已登记用量、
    更正原因为空）不改变修订号、不触碰存储。
  - 旧版本台账（无 revision 字段）照常读取，按修订号 0 兼容，首次成功提交后自动升级；
    存储损坏时就地提示，在操作员产出新数据前不写回，避免覆盖浏览器中的可追溯原文。
- **草稿隔离**：切换选中批次时，未提交的用量与备注草稿立即丢弃，不会误记到新批次；
  改变任一配液参数（或结果变为非法）时，「存入容量台账」的名称与额定容量草稿随旧结果一起重置。
- **领域契约**：`src/lib/capacityLedger.ts` 只暴露 `createBatch`、`recordUsage` 与
  `correctCapacity` 三个命令（纯函数，返回新状态，不修改传入状态），界面所有写入都经过这三个命令。

## 安全灯测试

从顶部「安全灯测试」入口进入，与配液计算、容量台账相互独立：

- **创建测试**：填写测试名称、起始秒数、递增秒数与条带数量（2–20 的整数）；
  末条曝光时长不得超过一小时（3600 秒）。名称为空、秒数 / 条带数量为非法整数
  （留空、小数、字母、非正整数、超出安全整数范围的超长数字）、末条超出一小时时
  在对应位置就地说明原因，不创建测试，也不影响已有数据。
- **阶梯曝光**：创建后页面按曝光顺序列出各条带时长（第 k 条 = 起始 + (k−1) × 递增），
  测试保持「待评估」，等待显影观察。
- **完成评估**：选择首条出现可见灰雾的条带（或「全部条带均未起雾」）后完成评估，
  结论由领域服务推导：首条起雾为第 k 条（k ≥ 2）时安全上限 = 第 k−1 条时长；
  首条即起雾时结论为「低于起始值」；全部未起雾时结论为「至少达到末条时长」。
  未选择观察结果直接提交会就地提示，不写入结论；结论一旦完成不可修改。
- **独立持久化**：测试草稿与已完成结论保存在独立的 localStorage 键
  （`darkroom.safelight-tests.v1`）中，与台账键互不影响，刷新后还原。
  存储内容损坏时就地提示，且在操作员产出新数据之前不写回，
  不会用空白状态覆盖浏览器中尚存的最近一次数据；
  写入前同样做序列化 → 反序列化往返校验，无法原样读回的状态拒绝写入。
- **领域契约**：`src/lib/safelightTest.ts` 只暴露 `createSafelightTest` 与
  `evaluateSafelightTest` 两个命令（纯函数，返回新状态，不修改传入状态），
  界面所有写入都经过这两个命令。
